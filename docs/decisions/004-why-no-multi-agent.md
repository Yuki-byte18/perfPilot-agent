# ADR 004：为什么不用多 Agent

- **状态**：已采纳
- **日期**：M3
- **相关**：硬约束 14「最多 1 主 Agent + 1 诊断 Agent」、硬约束 6、`packages/core/src/llm/`

---

## 背景

名字里带 "Agent" 的项目，默认期待是多 Agent 协作：诊断 Agent、方案 Agent、执行 Agent、
验证 Agent 互相传递消息、协商结论。这在演示里很好看 —— 你能画出一张有箭头的图。

问题是：**这些 Agent 之间到底要协商什么？**

## 决策

**最多 1 主 Agent + 1 诊断 Agent，且"Agent"在这里指的是 LLM 参与的两个具体环节，
不是一个自主循环的智能体。**

LLM 在本项目里只有两个位置：

1. **方案生成**（`core/llm`，M3 已落地）：对规则库覆盖不到的瓶颈提候选
2. **诊断解释**（规划中）：把已算出的瓶颈翻译成人话

决策、执行、验证**全部不用 LLM**。

## 理由

### 1. 这个项目的价值不在"协商"，在"可复现的测量与可回滚的补丁"

用户要的是一句话：

> 这次改动让 LCP 从 3.2s 变成 3.8s，原因是 `src/VirtualList.tsx:88` 的 `renderList`
> 阻塞主线程 220ms，建议改成虚拟滚动，改完验证过、没回归、已提 PR。

这句话里每一个数字都必须**可复现**。多 Agent 协商产生的结论是对话的产物，
不可复现、不可审计、出错了不知道该怪谁。

### 2. 实测：LLM 那一步经常一次都不触发

M3 的 planner 逻辑是「规则库覆盖不到才问 LLM」。
真实 CLI 跑下来（13 个瓶颈、18 种瓶颈种类）：

```
plan | ✅ ok | 产出 13 个候选（13 条来自规则库，0 条来自 LLM）
```

规则库已经覆盖全部 18 种瓶颈，LLM 是**兜底**。
把一个兜底环节扩成四个 Agent，是在优化一条几乎不走的路径。

### 3. LLM 不可用时链路必须完全可用 —— 而且实测确实可用

M3 验收里有一条：「LLM 输出校验失败自动降级为仅规则库，链路不中断」。
实测 `provider: none` 与「SDK 未安装」两种情况下，13 个候选全部正常产出。

多 Agent 架构会让这条降级路径变得极其复杂：主 Agent 挂了怎么办？
诊断 Agent 和方案 Agent 意见不一致怎么办？谁来仲裁？
**每一个都是一种新的失败模式，而它们全都只是在回答"没有 LLM 时怎么办"。**

### 4. LLM 的产出必须经过确定性层才能落地

即使 LLM 参与了，它的输出也要：

```
LLM 候选 → CandidateSchema 校验 → 决策层 Jev 评分与风险分级 → 才可能 apply
```

`core/decision` 被 ESLint 规则 + 依赖图断言双重禁止 import LLM（硬约束 7）。
**LLM 只能提方案，不能拍板。** 这个边界在多 Agent 架构里很难维持 ——
Agent 之间的消息传递天然会让"某个 Agent 做了决定"变得难以追踪。

## 取舍

**放弃了**：

- 多角色协商可能带来的"更全面的方案"（比如"方案 Agent"和"风险 Agent"争论后得到更稳妥的结论）
- 架构图上的箭头数量

**换来了**：

- LLM 完全不可用时系统照常工作（已实测）
- 每个结论都能追溯到"哪条规则命中 / 哪次 LLM 调用（带 `promptVersion`）+ 哪次决策计算"
- 成本可控：M3 的 LLM 只在规则库有缺口时调用，且有 `maxCostUsd` 硬上限

**判断标准**：什么时候该加 Agent？

当出现「**需要在一个开放的动作空间里反复试错，且中间结论无法用规则表达**」时。
性能优化不是这种场景 —— 它的动作空间是 18 类瓶颈 × 有限修法，
完全可以用规则库枚举，用期望值模型排序。
