# ADR 003：决策为什么用期望值模型（以及为什么不用托管的 Jev 服务）

- **状态**：已采纳（2026-10 修订：明确不接托管 Jev）
- **日期**：M4
- **相关**：硬约束 7「决策层禁止调用 LLM」、README §9、`packages/core/src/decision/`

---

## 背景

诊断给出的是"哪里有瓶颈"，方案给出的是"可以怎么改"。中间的**决策**要回答的是：

> 这 12 个候选里，哪些直接自动改？哪些出补丁等人确认？哪些只写进报告？哪些干脆别做？

这件事的本质是**在不确定性下做取舍**：

- 收益是**估**的（planner 说"预计省 80KB"，那是推算不是实测）
- 置信度是**估**的（规则命中 0.9、LLM 生成 0.6，都是我们自己定的）
- 成本是**估**的（改动面与投入）
- 但**回归风险是真实的** —— 改错了页面真的会坏

这正是期望值模型要解决的问题，因此项目一开始就定了"决策：Jev"。

## 决策

**用期望值效用模型做决策，但自己实现，不接入托管的 Jev 决策服务。**

实现落在 `packages/core/src/decision/utility.ts`：

```
utility = expectedGain × confidence − cost − λ × risk
```

四项分量全部是纯函数，可单独测试；`DecisionEngine.decide()` 是同步纯函数，
同输入必得同输出。

## 理由

### 1. "Jev" 是托管的神经决策模型，不是数学库

M4 期间做过一次完整调研（当时用户要求安装 `jev` 包）：

| 查证对象 | 结果 |
| --- | --- |
| npm `jev` | **`0.0.0` 空占位包**，2021-06 发布，无描述/无类型/无仓库，历史上只发过这一个版本 |
| `@scruple/provider-jev` | 源码要求 `apiKey: string`，默认 `model: "jev-1.13.0"`，内部调 `client.systemOne(...)` |
| `@typesafe-ai/sdk` | 自述是 "TypeScript SDK for the **TypeSafe API**" —— 托管服务客户端 |
| `jev-kit` / `@mlola/decision-jev` | 同为 TypeSafe Jev 生态的客户端/CLI |

旁证：[OpenRouter 收录了 Jev SDK](https://openrouter.ai/docs/guides/community/typesafe-sdk)、
[LiteLLM 有专门集成](https://docs.litellm.ai/blog/typesafe_jev)、
[有人拿它跑 8800 次做校准测量](https://zenn.dev/ryok/articles/jev-calibration-handson)。

结论：Jev 是一个**每次调用都要联网、要计费、结果由模型采样得出**的决策服务。

### 2. 与三条已定约束正面冲突

| 约束 | 出处 | 托管 Jev |
| --- | --- | --- |
| 决策层禁止调用 LLM | 硬约束 7 | ✗ 它就是模型 |
| 决策模块为纯函数，同输入同输出 | M4 验收 1 | ✗ 采样结果每次都不同 |
| 依赖图断言决策路径不含 LLM | M4 验收 5 | ✗ 直接违反 |

### 3. 最根本的一条：它抽掉这个项目的地基

整个项目的核心论点是：

> **敢在 CI 里自动改代码并回滚。**

这句话成立的前提是**决策可复现**。同一个 commit、同一份诊断，
今天判 `apply` 明天判 `reject`，这套自动化就没人敢开。
托管模型让"历史决策可复现"从工程问题变成不可能 ——
`Decision.thresholds` 快照能记录阈值，但记录不了模型的采样结果。

### 4. 期望值模型只有二十行，而且必须能被调试

M4 第一次跑真实数据时，12 个候选**全部被 reject**、utility 全为负：

```
⛔ reject | 将 assets/hero.png 转为 WebP | utility -25.7 | 收益×置信 0×0.90 | 成本 15 | 风险 11
```

排查下来的原因是两层量纲错配：权重被当成"缩小系数"用（导致收益趋近 0），
成本又按 0-100 铺开（一个单文件改动扣 15 分）。修法是改公式与刻度，
改完分布立刻正常（`apply 2 / confirm 6 / suggest 1 / reject 3`）。

**这类标定问题只能靠"读公式 + 改参数 + 重跑"解决。**
面对一个黑盒模型，你只能调 prompt 或换模型，无法定位"为什么这张图不值得优化"。

## 取舍

**放弃了**：

- 用更强的模型捕捉更细的权衡（比如"这个改动在 monorepo 里会引发连锁"）
- "我们接了 Jev" 这句话本身带来的标签感

**换来了**：

- 决策纯函数、零依赖、可单测（45 个测试覆盖六条验收标准）
- 无网络、无 API key、无按次计费，CI 里直接跑
- 出问题时可以精确定位到四个分量中的哪一个算错了

**已知代价**：

- 权重（LCP 0.35 / INP 0.25 / CLS 0.25 / 体积类 0.15）、成本刻度、风险基准、
  阈值（apply 30 / confirm 10）**都是手标的**，不是从数据里学出来的。
  需要在 M5 用「真实验证收益」反哺标定 —— 这正是 `Verification.gain` 要落盘的原因。
- 当前 planner 对部分规则的 `expectedGain` 估得过于保守
  （如"开启 Brotli 压缩"只给 4 分），导致本该自动做的 A 类优化被判 reject。
  这是 planner 的标定问题，决策层如实反映是对的，不该靠调松阈值掩盖。

**如果将来要接托管决策模型**，正确的位置是**「估算」而不是「拍板」**：

```
Jev  →  估算 expectedGain / confidence   （本来就是不确定的估算，适合模型）
纯函数 → 加权、扣成本、扣风险、比阈值      （必须确定性可复现）
```

即：让模型做它擅长的模糊判断，让算术做它擅长的可复现聚合。
**不要**让模型直接输出 `apply` / `reject`。
