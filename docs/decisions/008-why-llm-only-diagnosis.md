# 008 · 为什么 LLM 只能主导「诊断」，不能主导「决策」

## 背景

PerfPilot 名字里带 agent，用户自然期待"LLM 在干活"。但截至 M8，一轮 `run`
里 LLM 调用次数可以是 **0**：诊断靠 13 条确定性规则、决策靠一个四分量效用公式，
LLM 只在"规则库没给出候选"时兜底 —— 而规则几乎从不弃权，于是它等于没接。

真实缺口有两个：

1. **诊断只能认出"已知的问题形状"**。规则是逐来源、逐模式匹配的，
   而"这个页面为什么慢"是开放问题。例如某个长任务与某个第三方脚本的加载时间
   重合 —— 这需要跨来源关联（trace 的 `topFrame` × HAR 的请求时间），
   规则写不出来。
2. **用户看得见"没有 LLM"**。报告里没有任何 LLM 痕迹，也没有花费，
   于是"这是个 agent 项目"只是一个说法。

## 决策

把 LLM 放在**两处**，并且明确禁止第三处：

| 位置 | 由谁主导 | 产出 | 错了会怎样 |
| --- | --- | --- | --- |
| 诊断（`core/diagnoser`） | **LLM 可以主导** | `Bottleneck[]`（必须带证据） | 这条结论被丢弃，规则结论照旧 |
| 方案（`core/planner`） | LLM 全程参与 | `Candidate[]` | 降级为纯规则库 |
| 决策（`core/decision`） | **永远不行** | `Decision[]` | ESLint 硬性禁止 import `core/llm` |

同时给 LLM 的产出加三道闸：

1. **证据强制**：`LlmFindingSchema` 要求至少一条 evidence，没有证据的结论直接丢弃
2. **来源盖章**：`id` / `runId` / `source` 由我们生成，置信度上限 0.75
3. **合并限量**：与规则结论"同种类 + 同归因"的丢弃；每轮新增最多 5 条；
   `refines` 命中的结论是**覆盖归因**而不是另立一条

## 理由

**诊断可以不确定，决策不可以。**

- 诊断结论是**给人看的**：它带着证据、标注来源、可以复核。一条错的结论
  会被人看出来并忽略，代价是一条噪音。
- 决策结论是**给机器执行的**：它决定要不要改代码、要不要提交。
  一旦 LLM 参与，"同一份输入两次运行给出同一个裁决"就不成立，
  而 CI 门禁的全部可信度都建立在这句话上 —— 一个偶尔抽风的门禁
  比没有门禁更糟：它会让人开始无视红灯。

因此边界不是"LLM 强弱"的问题，而是**可复现性要求的不对称**：
诊断错得起，决策错不起。

三个附带的判断：

- **`provider: none` 必须是默认**。花钱的能力默认关着；配上 provider 就是
  明确表态"我要用它"。
- **成本必须累计**。诊断与方案两处调用共享 `maxCostUsd`，
  否则"每处都不超上限"合起来照样能超。
- **"没测到"不能变成"LLM 猜一个"**。零指标时直接跳过诊断 agent ——
  它在空白上生成的东西看起来最像诊断，也最危险。

## 取舍

- **决策的可复现性保住了，但"哪条修法被提出"不再可复现**：同一 commit 两次
  运行可能得到不同的候选（LLM 有温度）。门禁的通过与否仍然只由**实测指标**
  决定，与候选无关，所以这不影响 CI 语义 —— 但"上次它建议的改法这次没出现"
  会让人困惑，需要在报告里保留 `origin: llm` 与 `promptVersion` 以便追溯。
- **每轮多一次调用**（诊断 agent），钱和时间都要多花一份。默认关着，
  由用户显式开启；`maxCostUsd` 是硬刹车。
- **规则库仍然是地基**：它可复现、免费、覆盖了诊断器能产出的全部瓶颈种类。
  LLM 是增强层，不是替代品 —— 这一点写在 `planner.test.ts` 的
  "每一种瓶颈都有规则" 用例里。
