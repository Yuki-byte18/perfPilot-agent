# ADR 006：为什么执行器只产出 patch，不直接改工作区

- **状态**：已采纳
- **日期**：M5 前置决策（M4 期间定稿）
- **相关**：硬约束 8/9、`packages/shared/src/ports/executor.ts`

---

## 背景

M5 的执行器要把候选变成真实改动：AST 改写、图片转码、配置修改、依赖增删。
最直接的做法是**就地把文件改掉**，改完再验证——简单、少一层。

但对一个"敢在 CI 里自动改代码"的工具，这个选择决定了它能不能被信任。

## 决策

**执行器只产出 unified diff 文本，不直接修改工作区。**

```ts
export interface ExecutionResult {
  candidateId: string;
  route: ToolRoute;
  /** unified diff 文本，可直接 `git apply` */
  patch: string;
  /** 执行过程中是否已经改动了工作区（文本执行器恒为 false） */
  applied: boolean;
  /** `applied: false` 时含义是"将会改动的文件" */
  files: string[];
  summary: string;
}
```

唯一的例外是 `asset-processor`（图片转码需要写二进制），
它的 `ExecutionContext` 里才提供可选的 `writeFile`，且产物仍要能通过 git 撤销。

### 落地时补上的一个字段：`applied`

`applied` 不是设计时想到的，是 M5 接流水线时才暴露的缺口。

原先约定「`patch === ''` 且 `files.length > 0` 表示二进制改动已写入工作区」。
但 `asset-processor` 还有一个 `writeAssets: false` 的评估模式：它同样返回
`patch === ''` 和非空 `files`，**却一个字节都没写盘**（`files` 的含义是"将会改动"）。

两种状态在上层看起来完全一样，于是流水线会把"只评估过"的候选当成"已经落地"
拿去验证，然后拿着根本没变的指标去判断收益 —— 结果为 0，触发回滚，
回滚一个从未发生过的改动。加一个显式的 `applied`，两种状态才分得开。

## 理由

### 1. 补丁是唯一同时满足"可审计 + 可回滚 + 可人工确认"的产物

| 产物 | 可审计 | 可回滚 | 可人工确认 |
| --- | --- | --- | --- |
| 直接改工作区 | ✗ 只看到结果 | ✗ 要反推原状 | ✗ 无从确认 |
| 内存中的 AST 对象 | ✗ 看不见 | — | ✗ |
| **unified diff** | ✓ 文本 | ✓ 工作区回到基线 ref | ✓ 人能读懂 |

B 类（半自动）的整个流程依赖第三列：**生成 patch → 人工确认 → 再 apply**。
如果执行器直接改工作区，B 类就没有"确认"这个环节可以插入。

### 2. 硬约束 9「失败必须回滚，Git 即记忆」的前提是改动可完整撤销

回滚要回答"改回什么"。直接改工作区时，你必须自己记录原始内容——
这本质上就是在重新实现 git。

M5 最终选择的回滚方式**不是**反向应用 patch，而是 `git reset --hard <baseRef>`
加 `git clean -fd`：反向补丁只能撤销它自己引入的那点差异，
一旦执行过程中还有别的副作用（新建文件、依赖安装、二进制资产写入）就撤不干净。

这条选择反过来给流水线加了一个前置条件：**工作区必须干净**。
`reset --hard` 会连带丢掉开发者本地未提交的改动，所以在动手之前
先检查 `git isClean()`，不干净就一个补丁都不应用（补丁仍然产出）。
见 `Pipeline.prepareMutation`。

### 3. 直接改工作区会让"谁改的"变得不可分辨

CI 里跑完一轮，工作区里同时有：工具改的、开发者本地未提交的、依赖安装产生的。
出问题时无法区分，回滚时会误伤。

**patch 让工具的所有改动有明确的边界**：要么 apply 成功（改动都来自 patch），
要么没 apply（工作区完全没动）。没有中间状态。

## 取舍

**放弃了**：

- 少一层 apply 的简便性
- 二进制资产（图片）无法用它表达 —— 这是真实缺陷，`asset-processor` 必须例外

**换来了**：

- B 类候选的"人工确认"有了可插入的位置
- 回滚不需要自己实现，交给 git
- M5 的验证可以对 patch 先 dry-run 再决定是否 apply

**已知代价**：

- 图片转码的 diff 不直观（二进制 patch），报告中需要额外说明改了什么（转了什么格式、省了多少字节）
- 多一步 `git apply`，且需要处理 apply 冲突 —— 但这本来就是必须面对的问题，早点暴露比晚点好

**判断标准**：如果将来出现「**改动无法用文本 diff 表达，且无法用 git 撤销**」的场景
（比如直接操作远端 CDN 配置），那就不该放进 executor，
而应该生成"操作指令"交给人执行 —— 保持"工具不改不可撤销的东西"这条线。
