# ADR 005：为什么用线性流水线

- **状态**：已采纳
- **日期**：M1
- **相关**：ADR 002（不用 DAG）、README §3 执行链路

---

## 背景

ADR 002 讨论了"不用 DAG 引擎"。这个 ADR 回答一个不同的问题：
**这八段为什么是这八段，为什么是这个顺序，以及"跑到哪了"如何表达。**

## 决策

**八段固定顺序的线性流水线，每段产物独立落盘：**

```
collect → diagnose → plan → decide → execute → verify → keep/rollback → report
```

- 顺序由 `ALL_STAGES` 常量固定，不可配置
- "跑哪些段"由 `implementedStages` 决定（用于渐进交付与测试）
- 段内并行用 `Promise.allSettled`，段间严格串行
- 每段产出一份可校验的 JSON，落在 `.perfpilot/runs/<runId>/`

## 理由

### 1. 顺序是因果决定的，不是设计选择

"没采集就没诊断"不是一条规则，是一个事实。任何"可配置的段顺序"都会立刻产生
"诊断在采集之前"这种无意义配置。**把它做成可配置，等于把不可能的状态变成可表达的状态。**

### 2. 产物落盘让"中断后从任一点复现"成为可能

| 段 | 产物 | 用途 |
| --- | --- | --- |
| collect | `run.json` + `artifacts/` | 指标与原始证据 |
| diagnose | `diagnosis.json` | 瓶颈与归因 |
| plan | `candidates.json` | 候选方案 |
| decide | `decisions.json` | 裁决与阈值快照 |
| verify | `verifications.json` + `patches/*.patch` | 验证结论与补丁 |

这个设计的直接效果是**规则集升级后可以重跑诊断，而不重新采集**：

> `diagnose` 只读指标与产物，不重新采集。因此 `diagnosisId` 与 `runId` 不是一对一 ——
> 这也是两者分开落盘的原因。

如果流水线是"一个函数跑到底"，这个能力就不存在。

### 3. `stages` 数组让进度自描述

```ts
{ name: 'diagnose', status: 'ok',      durationMs: 11, note: '11/13 条规则命中，产出 13 个瓶颈' }
{ name: 'execute',  status: 'skipped', durationMs: 0,  note: '待 M5：执行' }
{ name: 'verify',   status: 'skipped', durationMs: 0,  note: '待 M5：验证与回滚' }
```

**报告本身就是进度表**，不需要另外维护一份"做到哪了"的文档。
未实现的段显式标 `skipped` + 里程碑编号，而不是从列表里消失 ——
读者能看到"这条链还有两段没接上"，而不是以为流水线就这么长。

### 4. 段与段的边界就是失败边界

每段独立 try/catch，失败策略逐段定义且不同：

| 段 | 失败时 |
| --- | --- |
| collect | 单 adapter 失败 → warning 继续；**全部失败 → 抛错**（避免"零指标绿灯"） |
| diagnose | 单规则失败 → warning 继续 |
| plan | 失败 → warning，报告仍出诊断部分 |
| decide | 单候选失败 → 降级为 `reject` 并记录理由 |

这种"每段各自的降级语义"在线性结构里一眼看得清；换成图结构，
失败会沿着边传播，需要额外一套策略来表达。

## 取舍

**放弃了**：

- 表达"跳过诊断直接执行某个手工候选"这类非线性流程
- 同一阶段的多轮迭代（执行→验证→再执行）

**补偿方式**：前一类需求在 **CLI 层**用参数处理（`--only A` / `--candidate <id>`），
而不是在 pipeline 里加分支。**在离用户最近的地方做特例，而不是把特例渗进核心引擎。**

**真正的边界**：M5 的「执行 → 验证 → 不达标则回滚」是一个**单层循环**，
仍然在线性模型的表达范围内（execute 段内部处理回滚，而不是在段之间来回跳）。

**判断标准**：当出现「**某一段需要根据前一段的输出决定是否回到更早的段**」时，
线性模型才需要让位。在那之前不需要。
