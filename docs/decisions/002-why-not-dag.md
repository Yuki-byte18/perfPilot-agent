# ADR 002：为什么不用 DAG 引擎

- **状态**：已采纳
- **日期**：M1
- **相关**：ADR 005（线性流水线）、硬约束 14「不用 DAG、不用拓扑调度」

---

## 背景

一个"性能诊断 Agent"听起来应该有条复杂的执行图：采集可以并行、诊断要等采集、
方案生成可以按瓶颈分叉、执行要串行……描述这套依赖最"专业"的做法是引入 DAG 引擎
（如 `dagre` / `topological-sort` / 自研调度器），把每个阶段声明成节点，让引擎解析依赖并调度。

问题在于：**这些依赖关系需要运行时解析吗？**

## 决策

**不引入 DAG 引擎，也不引入任何拓扑调度。** 流水线是一条固定顺序的直线，
唯一的并行是段内的同层 fan-out，用 `Promise.allSettled` 完成。

## 理由

### 1. 依赖关系是静态的，没有任何一步需要在运行时解析

八段的顺序由**因果关系**决定，不是设计选择：

```
没采集 → 没诊断 → 没方案 → 没决策 → 没执行 → 没验证 → 不能保留
```

这个顺序在编译期就完全确定。DAG 引擎的价值在于"依赖动态、节点数量不可预知"，
而这里两个条件都不成立。

### 2. 唯一真实的并行需求，一行就够

采集阶段确实需要并发：Lighthouse、构建产物扫描、HAR、trace 四个来源互相独立。
但这是**同层 fan-out**，不是跨层依赖：

```ts
const settled = await Promise.allSettled(usable.map((c) => c.collect(ctx)));
```

拓扑排序要解决的是"跨层乱序依赖"，我们没有跨层乱序依赖。
**并行度是一个数组的长度，不是一个调度器。**

### 3. 看起来最像要动态依赖的地方，也没用上

M2 的诊断阶段是规则集驱动的 —— `BUILTIN_RULES` 可插拔，13 条规则各自读不同产物。
这最像"需要依赖解析"的场景（哪条规则依赖哪个 adapter 的输出）。

实际做法是：**给所有规则同一个 `RuleContext`，顺序执行，逐条隔离异常**。

```ts
for (const rule of this.rules) {
  try { detections = await rule.detect(ctx) }
  catch (err) { logger.error(...); continue }   // 单条规则崩溃不影响其余
}
```

没有依赖声明、没有调度、没有失败传播策略 —— 因为 13 条纯函数读同一份上下文，
本来就不存在依赖关系。

### 4. 引入 DAG 要付的账

| 引入项 | 收益 |
| --- | --- |
| 节点定义 DSL | 0 —— 顺序已经写死在 `ALL_STAGES` 数组里 |
| 依赖解析器 | 0 —— 没有动态依赖 |
| 调度器 | 0 —— 段内 `Promise.allSettled` 已覆盖 |
| 失败传播策略 | 负 —— 现在的策略是明确的"单段失败→记 warning→继续或短路" |
| 一个新的调试对象 | 负 —— 排查问题时多一层抽象要看 |

**用 DAG 解决线性问题，是把复杂度当成了深度。**

## 取舍

**放弃了**：表达非线性拓扑的能力。以下需求在当前架构下无法直接表达：

- 用户自定义 stage 图
- 条件跳过一整条分支（如"只跑诊断不跑方案"）
- 同一阶段的多轮迭代（如"执行→验证→再执行"）

**部分补偿**：前两条用 `implementedStages` 配置 + `stages` 数组表达，
报告里直接显示每段 `ok / skipped / failed` 加里程碑备注 —— "做到哪了"是自描述的。

**真正的边界**：如果将来要做"多轮迭代优化"（执行→验证不达标→换方案再试），
那确实需要循环控制。但那是一个**单层循环**，仍然不需要 DAG。

**判断标准**：什么时候该重新考虑？当出现「**同一份配置下，两段之间的执行顺序会因运行时数据而不同**」时。
在那之前，线性是对的。
